# 助眠服务管理系统 · 项目实施路线文档

> 版本：V1.0　|　日期：2026-11-26　|　配套文档：《助眠服务管理系统 · 原型设计文档》V1.0
> 文档性质：实施顺序、阶段门禁、依赖与风险的管理文件，不含代码与数据库设计

***

## 1. 文档说明

### 1.1 编写目的

原型设计文档回答了「每个页面长什么样」，本文档回答另外三个问题：**先做什么、按什么顺序做、做到什么程度算完成**。它把 104 个界面拆成有依赖关系的实施阶段，为每一阶段设定可验证的通过标准，使项目推进过程可计划、可检查、可裁剪。

### 1.2 与原型文档的关系

| 文档       | 回答的问题           | 使用场景             |
| -------- | --------------- | ---------------- |
| 原型设计文档   | 界面长什么样、有哪些区块与状态 | 设计出稿、前端还原、测试用例编写 |
| 项目实施路线文档 | 先做哪块、谁依赖谁、何时算完成 | 排期、分工、评审、风险跟踪    |

两份文档共用同一套编号体系（U-xx / A-xx / U1\~U12 / A1\~A13），本文档中出现的界面编号均可直接回查原型文档。

### 1.3 术语约定

| 术语         | 含义                              |
| ---------- | ------------------------------- |
| 阶段（M0\~M6） | 项目实施的最小推进单元，每阶段以一次 Gate 评审收尾    |
| 周期（C1\~Cn） | **相对排期单位**，不代表日历时间；实际长度需按团队规模换算 |
| Gate（阶段门禁） | 进入下一阶段前必须全部满足的判据集合              |
| DoD（完成定义）  | 单个任务或阶段「算做完」的客观标准               |
| 工作包（WP）    | 可分配给一个人或一个小组的独立任务集合             |
| 流水推进       | 上一阶段未全部结束即启动下一阶段的可并行部分          |

### 1.4 使用方式

1. 每次 Gate 评审逐条核对判据，未通过不进入下一阶段，只允许「带条件通过」并登记遗留项。
2. 阶段内按工作包分配，工作包之间以接口契约解耦。
3. 需求变更统一走「变更影响表」：标注影响的阶段、界面编号与是否触发返工。

## 2. 项目概览

### 2.1 交付范围

| 端      | 形态                    | 模块数 | 界面数 | 编号范围                      |
| ------ | --------------------- | --- | --- | ------------------------- |
| 用户端    | 移动 H5（可嵌入小程序 WebView） | 12  | 49  | U-01 \~ U-49              |
| 管理端    | PC Web 后台             | 13  | 55  | A-01 \~ A-55              |
| 合计     | —                     | 25  | 104 | —                         |
| 可选（二期） | 两端社区                  | 2   | 6   | U-44 \~ U-46、A-51 \~ A-53 |

### 2.2 技术栈与工程约束

| 层次  | 选型                                          | 约束说明                        |
| --- | ------------------------------------------- | --------------------------- |
| 用户端 | HTML + Vue3 + Vite + Pinia + 移动端组件库         | 375 基准宽度，深色主题优先，首屏体积受控      |
| 管理端 | HTML + Vue3 + Vite + Pinia + PC 组件库         | 1440 基准，表格与表单密集型页面需做性能优化    |
| 服务端 | SpringBoot（Spring + SpringMVC + MyBatis 分层） | 按业务域分包，单体内按模块隔离，预留拆分边界      |
| 数据库 | MySQL8                                      | 统一字符集与时区，所有业务表带创建/更新时间与软删标记 |
| 缓存  | Redis                                       | 会话、验证码、时段占位锁、热点内容           |
| 存储  | 对象存储 + CDN                                  | 音频防盗链、图片压缩、上传直传             |
| 集成  | 短信、支付、推送、物流、IM                              | 全部通过适配层接入，禁止业务代码直连第三方 SDK   |

**三条硬约束：**

1. **双端同源**：用户端与管理端共用同一套 API 与状态枚举，禁止为某一端单独开「影子接口」。
2. **契约先行**：任何界面开工前，其依赖的接口契约必须已冻结；契约变更需评估双端影响。
3. **状态机唯一**：订单、预约、内容、计划的状态流转由服务端统一定义，前端只做展示映射。

### 2.3 规划原则

| 原则     | 依据                       | 规避的问题               |
| ------ | ------------------------ | ------------------- |
| 先底座后业务 | 104 个界面共享设计令牌、权限、上传、错误码  | 后期统一改造，返工成本成倍放大     |
| 先身份后数据 | U1/A1 是所有业务的前置依赖         | 各模块自造登录态，权限逻辑分裂     |
| 先消费后交易 | 内容、记录、计划是留存底座，交易依赖供给     | 先做商城导致「有货无内容」，演示空心化 |
| 外部依赖前置 | 支付、短信、存储、推送、IM 均有审批或接入周期 | 开发到中后期卡在资质上，整条线停摆   |
| 可选模块后置 | U10/A12 可整块裁剪，不影响主链路     | 早期投入分散，主链路延期        |

**读图要点：**

- 阶段之间存在**有意重叠**：M2 在 C2 即启动，是因为 M1 的登录与档案接口一冻结，内容域后端即可独立开发。

### 3.3 关键路径

```
M0 ──► M1 ──► M2 ──► M3 ──► M4 ──► M5 ──► M6
        │      │      │      │
        └──────┴──────┴──────┴──► 移动端 / PC 端两条前端线全程并行
```

**关键路径说明：**

| 依赖关系       | 原因                  | 若违反的后果             |
| ---------- | ------------------- | ------------------ |
| M1 → M2    | 睡眠记录必须挂在用户档案下       | 需要后期补数据迁移，历史记录无法归属 |
| M2 → M3    | 计划任务要引用音频与文章内容      | 计划任务为空壳，无法演示       |
| M3 → M4    | 咨询与商品需要「问题背景」才有购买理由 | 交易场景缺少转化入口，页面孤立    |
| M2/M4 → M5 | 人群包依赖行为与消费数据        | 圈选条件为空，推送无实际效果     |
| M0 → 全部    | 组件库与契约是所有页面的地基      | 每阶段重复造组件，样式不统一     |

**可并行启动的边界条件：**

| 并行线              | 启动条件         | 不必等待    |
| ---------------- | ------------ | ------- |
| PC 端列表/表单/图表三套模板 | M0 组件库就绪     | M1 全部完成 |
| 内容域后端            | 内容表结构与接口契约冻结 | M1 前端完成 |
| 计划域与测评域后端        | 量表与计划的配置模型冻结 | M2 前端完成 |
| 服务域后端（排班、时段锁）    | 助眠师与排班模型冻结   | M3 全部完成 |
| 交易域后端（SKU、订单状态机） | 商品与订单状态机冻结   | M4a 完成  |
| 视觉高保真            | M0 设计令牌定稿    | 任何开发阶段  |

## 4. 各阶段实施明细

### 4.1 M0 底座与契约（C1）

**阶段目标**：把所有页面将要共用的东西先做对——设计令牌、通用组件、路由骨架、接口契约、数据库基线、部署流水线。这一阶段不产出任何业务功能，但决定后续所有阶段的速度。

**覆盖界面**：无业务界面，仅建立 104 个路由占位与页面骨架。

| 工作包         | 内容                                                                                           | 产出物                       |
| ----------- | -------------------------------------------------------------------------------------------- | ------------------------- |
| WP0-1 设计令牌  | 将原型文档第 2 章的色板、字号、圆角、间距、阴影落成 CSS 变量与双端主题文件                                                    | 令牌文件 + 主题预览页              |
| WP0-2 通用组件  | 原型文档第 6 章 18 个通用组件：底部 Tab、顶部导航、卡片、空态、骨架屏、Toast、弹层、确认框、步进器、侧栏、筛选条、表格、分页器、状态标签、抽屉、弹窗、图表容器、金额展示 | 组件库 + 预览页（Storybook 或等价物） |
| WP0-3 路由骨架  | 双端 104 个路由占位，按模块分组，配置权限元信息                                                                   | 可点击的空白页面集合                |
| WP0-4 接口契约  | 先冻结 U1/A1 两组接口；统一响应结构、错误码表、分页参数、状态枚举                                                         | OpenAPI 文档 + 错误码表         |
| WP0-5 数据库基线 | 用户、内容、计划、测评、助眠师、预约、商品、订单、消息、日志十组核心表的结构基线                                                     | 建库脚本 + 数据字典初稿             |
| WP0-6 工程环境  | dev/test/prod 三套环境、CI 流水线（构建 + 自动部署测试环境）、日志规范、健康检查                                           | 可部署的流水线                   |

**Gate 判据：**

1. 双端均可在测试环境访问，登录页能打开，104 个路由不出现白屏。
2. 组件库覆盖第 6 章全部组件，且每个组件有独立预览与使用示例。
3. U1/A1 接口契约评审通过，字段与状态枚举冻结；错误码表不少于 20 条且双端已接入统一处理。
4. CI 能从提交到部署测试环境全自动完成，失败有明确日志。

**主要风险**：组件库做成「大而全」拖慢进度。对策是只做原型文档中已出现的组件，未出现的组件一律不做。

***

### 4.2 M1 账号与权限（C1\~C2）

**阶段目标**：打通「能进来、能管人、能留痕」，让后续所有业务有可信的身份基础。

**覆盖界面**：U-01、U-02、U-03、U-04、U-05、U-06（6 个）；A-01、A-02、A-03、A-04、A-05（5 个）；A-55（1 个）。合计 12 个。

| 工作包         | 内容                                | 对应界面           |
| ----------- | --------------------------------- | -------------- |
| WP1-1 用户准入  | 启动分流、验证码/密码登录、注册、找回密码、首次三步建档、协议授权 | U-01 \~ U-06   |
| WP1-2 管理员认证 | 登录、找回密码、首次登录强制改密、连续失败锁定           | A-01、A-02      |
| WP1-3 RBAC  | 管理员账号、角色、菜单权限树、数据范围（全部/本部门/仅本人）   | A-04、A-05      |
| WP1-4 工作台   | 按角色动态渲染指标卡、待办与快捷入口                | A-03           |
| WP1-5 审计日志  | 登录、权限变更、敏感数据查看等操作的埋点与查询           | A-55           |
| WP1-6 文件上传  | 头像、资质证书等图片上传，走对象存储直传              | U-05、U-48、A-04 |

**Gate 判据：**

1. 新用户可完成「注册 → 三步建档 → 进入首页」，中途退出可续填。
2. 三种典型角色（超管、运营、客服）登录后可见菜单存在明确差异，且接口层面同样拦截。
3. 越权访问返回统一无权限态，不泄露数据是否存在。
4. 查看完整手机号、导出、权限变更三类敏感操作在 A-55 可查到完整记录。

**主要风险**：短信通道未就绪。对策是 M0 即提交签名报备，开发期使用固定验证码白名单，Gate 前切换到真实通道验证一次。

### 4.3 M2 数据与内容（C2\~C4）

**阶段目标**：建立产品的核心使用价值——记录昨晚睡得如何，并给出今晚该听什么。这是留存的基础，也是后续计划、测评、交易的素材来源。

**覆盖界面**：U-07 \~ U-21（15 个）；A-09 \~ A-19（11 个）；A-06/A-07 的基础图表（2 个）。合计 28 个。

| 工作包        | 内容                                     | 对应界面                      |
| ---------- | -------------------------------------- | ------------------------- |
| WP2-1 首页聚合 | 睡眠概览卡、今日计划卡（占位）、快捷入口、推荐位、下拉刷新          | U-07                      |
| WP2-2 睡眠记录 | 补录/编辑、日报、周报、趋势分析、日历、报告计算规则             | U-12 \~ U-16              |
| WP2-3 内容消费 | 知识列表与详情、搜索、分类页、播放器、混音器、定时关闭、收藏与歌单、课程详情 | U-08 \~ U-11、U-17 \~ U-21 |
| WP2-4 内容生产 | 音频管理、音频编辑、文章管理、分类标签、审核队列、播放数据          | A-14 \~ A-19              |
| WP2-5 用户管理 | 用户列表、详情、睡眠档案、标签分群、账号状态                 | A-09 \~ A-13              |
| WP2-6 基础看板 | 运营总览与用户睡眠看板的指标卡与趋势图                    | A-06、A-07                 |
| WP2-7 媒体能力 | 音频转码、防盗链、断点续传、封面压缩                     | 支撑 U-17 \~ U-21           |

**Gate 判据：**

1. 补录一条睡眠记录后，日报、周报、日历、趋势四处数据一致，且时间不合理时无法保存。
2. 后台上传音频 → 审核 → 上架 → 用户端搜索到并可播放，全链路无人工改库。
3. 后台下架内容后，用户端在 5 秒内变为「内容已下线」并停止播放。
4. 播放器支持锁屏控制、后台播放、定时关闭，弱网下缓冲与失败提示符合原型定义。
5. A-11 睡眠档案能按日期区间展示明细与趋势，手动补录的数据带「手动」来源标记。

**主要风险**：报告计算规则含糊导致反复返工。对策是在 WP2-2 开工前先书面确认评分与达标口径，并做成可配置参数（A-54 已预留）。

### 4.4 M3 干预与测评（C4\~C5）

**阶段目标**：从「看数据」进阶到「有方法」——用户能被安排计划、被评估状态，形成持续使用的理由。

**覆盖界面**：U-22 \~ U-29（8 个）；A-20 \~ A-27（8 个）；A-23（1 个）。合计 17 个。

| 工作包         | 内容                            | 对应界面                   |
| ----------- | ----------------------------- | ---------------------- |
| WP3-1 计划引擎  | 计划的日程模型、任务类型、加入/退出、进度计算、补卡规则  | U-22 \~ U-24、A-20、A-21 |
| WP3-2 打卡与成就 | 每日打卡、打卡日历、连续天数、徽章获取与展示        | U-24、U-25、A-22、A-23    |
| WP3-3 量表引擎  | 量表结构、题目与维度、分值、分级区间、解读文案，全部可配置 | A-24、A-25              |
| WP3-4 测评作答  | 答题页、进度保存、提交、结果页、历史记录与趋势       | U-26 \~ U-29           |
| WP3-5 测评数据  | 测评记录查询、答卷回看、群体统计              | A-26、A-27              |

**Gate 判据：**

1. 运营在后台新建一个 7 天计划并配置每日任务，用户端可完整执行到第 7 天并拿到徽章。
2. 后台新建一份量表（含分级与解读），用户端答题后得到正确等级与建议文案，无需改代码。
3. 已发布量表修改题目后，历史答卷与结果保持不变，且仍可查看。
4. 分级区间重叠或断档时后台拒绝保存，并指出冲突区间。
5. 打卡中断、补卡超限、计划下架三种异常场景的用户端表现与原型一致。

**主要风险**：量表涉及医疗表述。对策是所有结果文案内置免责声明，等级措辞限制为「良好 / 轻度 / 中度 / 重度」描述性表达，不出现诊断结论。

### 4.5 M4 服务与交易（C5\~C7）

**阶段目标**：跑通付费闭环，把内容与专业服务变成收入。这是全程最长、耦合最多、外部依赖最重的阶段，必须拆成两个子阶段推进。

**覆盖界面**：U-30 \~ U-40（11 个）；A-28 \~ A-42（15 个）；A-10 关联 Tab。合计 26 个。

#### 4.5.1 M4a 服务预约（C5\~C6）

| 工作包          | 内容                       | 对应界面           |
| ------------ | ------------------------ | -------------- |
| WP4a-1 供给管理  | 助眠师列表、资料与定价、入驻审核、排班与可约时段 | A-28 \~ A-31   |
| WP4a-2 发现与预约 | 助眠师列表、详情、时段选择、预约确认与支付    | U-30 \~ U-33   |
| WP4a-3 咨询会话  | 图文/语音/视频会话、消息状态、次数与结束规则  | U-34           |
| WP4a-4 预约管理  | 预约单列表与详情、改约、取消、退款审批      | A-32、A-33、A-35 |
| WP4a-5 合规与质量 | 会话监管、敏感词拦截、评价与差评跟进       | A-34、A-36      |

**M4a Gate 判据：**

1. 同一时段被两人同时预约时，只有一人成功，另一人收到明确提示且无脏数据。
2. 「预约 → 支付 → 进入会话 → 结束 → 评价」全链路可演示，支付失败可重试且订单保持待支付。
3. 助眠师请假后，已约用户收到改约通知，未约时段立即不可选。
4. 管理端退款后，用户端订单状态与消息同步更新，金额与规则计算一致。

#### 4.5.2 M4b 商品交易（C6\~C7）

| 工作包          | 内容                                | 对应界面           |
| ------------ | --------------------------------- | -------------- |
| WP4b-1 商品    | 商品列表、SKU 矩阵、库存预警、上下架              | A-37、A-38      |
| WP4b-2 购买链路  | 商城首页、商品详情、购物车、订单确认                | U-35 \~ U-38   |
| WP4b-3 订单履约  | 订单列表与详情、发货、物流、关闭订单                | A-39、A-40、U-39 |
| WP4b-4 售后与资金 | 退款售后、对账流水、助眠师结算                   | A-41、A-42      |
| WP4b-5 会员基础  | 会员方案与权益、用户端会员中心（先做权益生效，营销玩法留到 M5） | A-43、U-40      |

**M4b Gate 判据：**

1. 下单 → 支付回调 → 发货 → 确认收货 → 评价全链路可演示，重复回调不产生重复订单状态。
2. 库存为 0 时商品自动售罄，用户端同步置灰，不能下单。
3. 退款金额按规则计算，可人工下调不可上调，退款流水在 A-42 可核对。
4. 会员价、优惠券、运费三者在结算页的计算结果与后端一致，四舍五入规则统一。

**主要风险：**

| 风险       | 对策                                  |
| -------- | ----------------------------------- |
| 支付资质未批   | 支付网关抽象层，沙箱通道与真实通道可切换，业务代码零改动        |
| IM 自研成本高 | 优先使用成熟 IM 服务，若自研则限定文本 + 图片 + 语音三种消息 |
| 金额计算分歧   | 所有金额以「分」为单位存储与计算，展示层统一格式化           |
| 状态机混乱    | M4 开工前先产出订单与预约的状态流转图，评审通过再编码        |

### 4.6 M5 触达与运营（C7\~C8）

**阶段目标**：让已有用户被召回、被转化，并补齐管理层需要的数据视图。

**覆盖界面**：U-41 \~ U-43（3 个）；A-44 \~ A-53（10 个）；A-06 \~ A-08 完整看板（3 个）。社区 U-44 \~ U-46、A-51 \~ A-53 为可选项。合计 13 个必做 + 6 个可选。

| 工作包          | 内容                         | 对应界面                      |
| ------------ | -------------------------- | ------------------------- |
| WP5-1 消息中心   | 消息分类、未读、通知详情、睡眠提醒设置        | U-41 \~ U-43              |
| WP5-2 消息配置   | 模板管理、推送任务、站内信与公告           | A-48 \~ A-50              |
| WP5-3 营销规则   | 优惠券、活动与限时营销、营销效果分析         | A-44、A-45、A-47            |
| WP5-4 人群运营   | 人群包圈选、画像预估、跳转推送            | A-46                      |
| WP5-5 看板补全   | 运营、用户睡眠、交易三张看板的完整图表与导出     | A-06 \~ A-08              |
| WP5-6 社区（可选） | 信息流、发布、详情评论；动态审核、评论管理、举报处理 | U-44 \~ U-46、A-51 \~ A-53 |

**Gate 判据：**

1. 推送任务可按人群包发送，频控超限时被拦截，发送结果可查看送达与失败数。
2. 用户处于免打扰时段时，推送被延后或抑制，站内信正常展示。
3. 券与活动叠加时的最终价与规则一致，停用券后未使用券立即失效。
4. 三张看板的数据口径与业务列表可对上（抽查任意一天）。
5. 若启用社区：屏蔽一条动态后用户端立即不可见，举报处理结果以站内信通知双方。

**主要风险**：营销规则组合爆炸。对策是限定可叠加组合（券 + 会员 + 活动最多两层），并在 M5 开工前写死优先级顺序。

## 7. 范围裁剪与优先级

### 7.1 优先级矩阵

| 优先级    | 判定标准          | 覆盖范围                                  | 缺失后果                    |
| ------ | ------------- | ------------------------------------- | ----------------------- |
| P0 不可裁 | 缺任一环节，产品主线讲不通 | U-01\~U-21、U-47\~U-49；A-01\~A-19、A-55 | 无法形成「记录 → 内容 → 消费」的基础闭环 |
| P1 应做  | 构成完整商业闭环      | U-22\~U-40；A-20\~A-42、A-43            | 有用户无收入，无法验证商业模式         |
| P2 可延后 | 不影响主流程演示      | U-41\~U-46；A-44\~A-53                 | 少召回与运营手段，核心体验完整         |
| 二期     | 需额外资质或硬件      | 社区、混音器高级能力、智能唤醒、深度看板                  | 不影响一期验收                 |

### 7.2 三种压缩路径

**路径 A：完整产品化（多角色团队）**

按 M0 → M6 全量推进，104 个界面全部交付，社区作为可选模块同步建设。

**路径 B：单人 / 小团队（推荐用于期限紧张的场景）**

| 调整        | 具体做法                              | 保留界面数 |
| --------- | --------------------------------- | ----- |
| 交易只保留服务预约 | M4b 仅做商品浏览与订单展示，支付走沙箱不接真实通道       | 约 90  |
| 运营整体降级    | M5 只做消息中心 + 站内信，不做人群包、券、活动、推送任务   | 约 78  |
| 社区移入二期    | U10/A12 整块关闭，入口按原型文档的「未开通时隐藏」规则处理 | 约 72  |
| 看板只做一张    | 只保留运营总览，用户睡眠与交易看板移入二期             | 约 70  |

该路径仍可覆盖约 70 个界面，主链路（注册 → 记录 → 内容 → 计划 → 测评 → 咨询 → 预约支付）完整可演示。

**路径 C：演示优先（教学 / 评审场景）**

优先保证每阶段都有可演示的完整故事线，允许部分管理端功能使用静态数据。原则是：**用户端真实可用，管理端可演示可操作**，但统计类页面允许接静态数据。

### 7.3 裁剪执行规则

1. 裁剪必须整模块进行，不拆散模块内部界面，避免出现「有列表无详情」的断裂。
2. 被裁剪模块的前端入口一律隐藏，但路由保留，便于二期直接开启。
3. 被裁剪模块对应的数据表结构仍在 M0 建好，避免二期做数据迁移。
4. 裁剪决定需在对应阶段 Gate 前做出，阶段中途裁剪会造成返工。

## 9. 质量与验收机制

### 9.1 阶段完成定义（DoD）

每个工作包完成需同时满足：

1. 页面或接口的功能与原型文档描述一致，布局区块不缺项。
2. 原型文档第 6.3 节的六种状态（加载、空、错误、无权限、离线、登录失效）已实现。
3. 对应接口已联调，不再是本地 Mock。
4. 数据库变更以脚本形式提交，可在空库一键重建。
5. 关键路径有测试用例，且用例已执行通过。
6. 接口文档同步更新。

### 9.2 测试分层

| 层级    | 覆盖对象             | 责任方     | 通过标准                    |
| ----- | ---------------- | ------- | ----------------------- |

| 兼容测试  | 移动端主流机型与浏览器      | 测试      | 375 / 390 / 414 三档宽度无错位 |
| 性能测试  | 首页、列表、报告、结算、支付回调 | 测试 + 运维 | 高峰期响应与错误率达约定阈值          |
| 安全测试  | 越权、脱敏、上传、重复提交    | 测试      | 高危问题为零                  |
